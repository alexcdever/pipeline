## 改了什么（对齐同一位置的 `head` 修复）

同一位置的 `head` 判定此前已放宽为 `head_advanced_by_evidence_only`；本任务处理剩余的 `branch`/`worktree`，**只增加一条**可机械证明的放宽路径，其余判定与错误文本逐字不变。

- `pipeline_tools/core.py:2682` 新增 `merged_task_branch_identity(root, report, task_id, head_accepted)`。三条同时成立才返回 True：
  1. 报告的 `branch` 在本仓库以 `refs/heads/<branch>` 解析成功，且 `git merge-base --is-ancestor refs/heads/<branch> HEAD` 返回 0（已并入当前 HEAD）；
  2. 报告的 `worktree` 解析后等于 `<root>/.worktrees/<task-id>`（`task_id` 取报告与调用方一致的 task id，且经 `_safe_task_identifier` 校验）**且该路径真实存在**（`is_dir()`）；
  3. 传入的 `head_accepted` 为真，即报告的 `head` 已通过既有 `head_advanced_by_evidence_only` 判定。
- `pipeline_tools/core.py:553-579`（`evidence_verify` 内）把 `head` 判定提取为 `head_accepted` 变量（判定逻辑与错误文本不变，`:560`），并让 `branch` 身份错误（`:569`）、`worktree` 身份错误（`:576`）与显式 `--branch` 的 `branch mismatch`（`:578`）在 `merged_identity` 为真时不再追加。
- 未动 `head` 的任何语义：`head_accepted` 为假时三条放宽路径全部失效，报告仍按严格规则报错。
- `pipeline_tools/core.py:559-562`、`:2653-2679` 的两个既有辅助函数未改。

**一处必须由主代理确认的判读**：`--branch` 显式传入且与报告不符时，旧代码在 `:563` 与 `:572` 对同一个条件报两次错（`branch does not match current Git identity` 与 `branch mismatch`，后者与前者等价、纯冗余）。三条放宽条件成立时，本实现把这两条**一起**放宽——否则传入 `--branch main` 的合并后调用永远过不去，而简报里复现的真实失败正是 `--branch main` 的调用（六条错误含两条 `branch mismatch`）。文档（`SKILL.md`、`references/merge-and-recovery.md`）按此语义写明"显式 `--branch` 只用于声明当前身份，不构成额外放宽"。若主代理的意图是"显式 `--branch` 不符时永远报错"，则需要重新裁决，因为那样合并后的调用仍会以退出码 3 失败。
