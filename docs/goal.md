# 编程流水线技能实施计划

## 目标

将本技能从“人工编排执行、审查和合并”的流程，扩展为能够依据本文件描述的已冻结需求，自动分析项目事实、规划垂直功能任务、生成任务单，并由脚本对规划结果和执行证据实施机械闸门。

## 范围

- 在任何规划动作前执行规划前置检查。
- 固定项目需求权威文件为 `docs/goal.md`；兼容解析顺序为 `docs/goal.md`、仓库根目录旧版 `goal.md`、更旧的 `implement-plan.md`。缺少 canonical 文件时将首个 legacy 来源迁移到 `docs/goal.md`。
- 区分需求事实、项目事实、假设、未知和冲突。
- 让大语言模型负责项目语义分析、垂直任务拆分和验收测试设计。
- 让 Python 工具负责结构、路径、引用、依赖、身份、范围、证据和生命周期事实检查。
- 每个用户功能任务覆盖外部入口、交互、应用处理、领域事实、持久化、重新读取和恢复。
- 每个外部操作至少绑定一个完整名称的验收测试。
- 支持 `vertical-feature`、`prerequisite` 和 `repair` 三种任务类型；历史 `derived` 契约只保留读取兼容，新任务不再从父任务派生。
- 每次任务从主工作树创建唯一的实现 worktree；任务之间的接替关系用 `dependencies` 表达。
- 任务单契约在合并前按修订版本演进：执行子代理和审查子代理可提交契约缺陷反馈，由主代理裁决并修订任务单，记录理由、发起角色与裁决引用；修订不受阶段限制。合并后不再修订，需求变化重新规划。
- 契约松动（删除或放宽验收测试、降低证据等级、扩大允许范围）必须记录裁决引用；收紧不受此限。
- 任务完成后，任务单移入其证据目录 `.pipeline/<task-id>/`；没有对应证据目录时移入 `.pipeline/archive/`。`docs/tasks/` 只保留进行中或待派发的任务单。
- 使用角色进度日志记录执行过程；进度日志不进入 Git。
- 成功最终化后只保留阶段报告、机器结果和最终化标记；失败时保留完整现场但不提交、不合并、不清理。
- 默认允许主代理自动推进后续任务，并支持项目或当前运行切换为逐任务人工确认。

## 非目标

- 不让 Python 脚本理解自然语言需求或替代大语言模型做产品判断。
- 不自动修改本文件、不自动安装或替换 Git、Python 或项目依赖。
- 不自动合并 Git 分支。
- 不把失败现场、原始日志或进度日志作为成功交付物。
- 不把技术层任务冒充完整用户功能。

## 需求事实

规划器必须从本文件提取资源、操作、链路、边界和验收总原则；本文件不强制固定章节结构，脚本只检查存在、可读、非空、无占位符和哈希稳定性。需求解释存在多义冲突且不能依据本文件和当前事实唯一判断时，主代理必须暂停并请求开发者裁决。

## 数据和状态要求

- 规划前置检查失败时不得生成可冻结任务单、创建工作树或派发子代理。
- 规划成功时中间结果默认不落盘；任务单生成失败时不写任何审计文件，直接把失败结果返回给人类开发者裁决；其他规划失败、中断、冲突或需要审计时，才保存到 `.pipeline/planning/<planning-run-id>/`。
- 进行中的任务单保存于 `docs/tasks/<task-id>.md`，已终态的任务单保存于其证据目录 `.pipeline/<task-id>/`，没有对应证据目录时保存于 `.pipeline/archive/`；任务证据保存于 `.pipeline/<task-id>/`，工作树保存于 `.worktrees/<task-id>`。
- `docs/goal.md` 哈希在规划、任务生成和执行期间必须稳定；需求变化必须重新规划。
- 没有已提交且冻结的任务单不得存在对应任务工作树。
- 任务单修订必须留痕：每次修订追加一条记录，含前版与新版哈希、理由、发起角色、裁决引用和结构性差异；未经记录的修改视为静默篡改，必须被机械检测拦截。过程记录写入角色进度日志，不写入任务单。

## 验收总原则

- 规划前置检查必须检查 `docs/goal.md`（并按兼容顺序处理旧版根目录来源）、Git、Python、本技能工具、主工作树身份、已有任务现场和 `.workflow`/`.pipeline` 冲突。
- 项目事实必须先通过结构和机械事实校验，再交给大语言模型分析。
- 任务计划必须覆盖所有需求、资源和外部操作；非目标必须显式记录。
- 每个外部操作至少有一个对应验收测试；单个资源操作和批量操作分别建模。
- 每个 `vertical-feature` 和 `repair` 任务必须覆盖完整链路；证据等级按项目类型和功能风险动态确定。
- 执行、独立审查、主代理终审必须分别生成 Markdown 报告和机器结果。
- 每份阶段报告和机器结果必须写明它评判的任务单修订版本；修订触及验收测试、范围、链路、风险或证据下限时，已有的阶段证据作废，必须对最新版本重做独立审查。
- “是否改变验证面”与“是否放松约束”是两个独立判据，两者都不得用于迁就实现结果。
- 成功最终化后不得引用已删除的原始日志；失败或阻塞不得创建最终化标记。
- 所有测试编号使用完整名称，例如“验收测试1”或 `acceptance-test-1`，不得使用英文首字母缩写。
