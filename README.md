# pipeline

一份纯流程契约：规定 agent 在开发编程项目时，主代理、执行子代理、审查子代理怎么协作，什么算完成，什么不算。

**没有脚本、没有工具、没有运行时。** 只有一份流程契约、一份术语表、一份残留恢复手册，加一份一次性的迁移说明。

## 文件

| 文件 | 作用 |
|---|---|
| `SKILL.md` | 流程契约本身——**规则都在这里，也是唯一的权威** |
| `RECOVERY.md` | 残留恢复手册：{登记, 目录, 分支} 三态表（八种组合）、并入判法、repair 与重挂、清场变体。**只在盘点发现残留时才读**，正常任务用不到 |
| `ENVIRONMENT.md` | 环境事实：git 与 Windows/PowerShell 的实测行为（`SO_REUSEADDR` 双监听、`git -C` 静默向上解析、`info/exclude` 裸通配静默跳过等）。**它解释判据的来历，不新增规则**；正文需要理由时才查 |
| `TESTING.md` | 测试机制层：测试怎么分档（单进程/单机/跨机）、push 检查要满足的六条、怎么故意让它失败一次来验证。`SKILL.md`「全量测试」节的判据细节全在这里 |
| `PROTOCOL.md` | 执行层协议：宿主侧命令执行设施返回给 agent 的通用外壳（JSON schema、字段含义、`degraded` 标记规则）。`SKILL.md` 只要求「输出可回查、退出码不能代替验收」，包装格式在这里 |
| `GLOSSARY.md` | 术语表 |
| `FLAKY.md` | 不稳定测试排除清单的**模板**：用途、移出日期的含义、四列格式、判定方法、14 天后会发生什么。第一次真的移出时才复制进项目，位置跟着测试代码走 |
| `MIGRATION.md` | 从前一版（带 `pipeline_tools` 的那版）迁过来的一次性清理清单。**不是契约的一部分** |

## 用词也归它管

契约里有一节「用词」：这套流程产出的文字用日常的中文词、缩写第一次出现写全称、项目里的东西用它本来的名字、编号不当名字用。**下游多半是 AI**，写下来的话会被下一轮的 AI 当成「已经确立的说法」再抄一遍，所以这条约定待在 `SKILL.md` 里，不放成一份没人会点开的风格文档。

## 用起来

把整个目录放进宿主的技能目录——`SKILL.md` 会引用同目录的 `GLOSSARY.md`、`RECOVERY.md`、`ENVIRONMENT.md`、`TESTING.md`、`PROTOCOL.md` 与 `MIGRATION.md`，单读它一份会让那几处引用悬空。`RECOVERY.md` 只在盘点发现残留时才需要读，`ENVIRONMENT.md` 只在要弄清「为什么判据长这样」时才需要读，但文件都得在场。

**用之前先看 `SKILL.md` 的「硬前提」。** 不满足的话，这个技能不适用——它没有降级模式，也不接受同一个上下文既实现又审查。

## 全量测试是硬要求

**项目里全部自动化测试跑一遍，要在四个地方各跑一次、各是绿的**：执行者回报完成前、审查者下结论前、主树复验时、含代码文件的提交被 push 到远端之前。前三个靠角色纪律（各自跑、各自的结论里写下命令与结果），**最后一个必须由项目侧自动化强制**——只在流程里要求没用，用户手工 push、别的 agent push 都绕得过去。

**但那道检查挂在哪里、长什么样，本技能不做规定。** 契约只写「必须机器强制」；六条判据、分层（快速集合/全量集合）、push 检查怎么验证它真能拦，都收在同目录的 `TESTING.md` 里。

## 测试分档与「自带环境」的出处

「全量测试」一节里那套按资源分三档（单进程 / 单机 / 跨机）而不是按代码量分层的做法，来自 *Software Engineering at Google*（Titus Winters 等编，O'Reilly 2020）第 11 章「Testing Overview」。该书的免费 HTML 版在 `abseil.io/resources/swe-book/html/ch11.html`，原文把 **test size**（用什么资源）和 **test scope**（验多少代码）明确区分成两个维度，并指出尺寸定义可以是**测试基础设施能强制的约束**（例：Java 里标为 small 的测试若尝试建立网络连接会被判失败）。本章同时说明：团队配比只是粗略经验值、各团队不同；覆盖率只衡量「这行被跑到」而非「跑出了正确结果」，因此把覆盖率当目标会让人把它当天花板而不是地板。「备择比例」一节记录的就是这些经验值，不构成契约。

「任务间并行」一节里「先让测试自带环境、再给剩下的分配实例」的顺序，同样出自该章对 hermetic 测试的要求：一条测试应包含建立、执行、拆除其环境所需的全部信息，不依赖共享数据库、不假设执行顺序。

**本技能不照抄该书的任何比例数字**（书中 80/15/5、Google 测试博客 70/20/10 等），也刻意不要求代码覆盖率——那些是 Google 在其规模下的经验值，写死成阈值只会变成形式主义。照抄的只有三条判据：按资源分类、约束要能被工具强制、测试自带环境。

> 附带一条只在恢复时才用得上的经验值：书中给出的不稳定率经验是「接近 1% 时测试开始失去价值」，Google 自己维持在 0.15% 左右。本项目若不稳率明显偏高，第 12 条「四处各跑一次」会频繁因与改动无关的原因变红——那不是规则有问题，是测试集合需要治理，按第 9 条交用户裁决怎么治，别默默重跑。


## 这里没有的东西：三个常被混起来的名词

下面三件事经常被当成一回事，本技能只处理第三件。

| 名词 | 是什么 | 本技能怎么对待 |
|---|---|---|
| **混沌工程**（Chaos Engineering） | 给**生产或仿真环境**主动注入故障（杀实例、断网、加延迟），看系统扛不扛得住。目标是系统韧性，是一套实践，不是某个测试框架。主要取决于部署平台，跟语言生态关系不大 | **不写进契约。** 它服务的是「系统在故障下怎么反应」这类标准，不是每个任务都有。有这类标准时，把它当成一条验收标准的实现方式即可，不必额外规定 |
| **不稳定测试**（flaky test） | 同一份代码、同一条命令，有时过有时不过。**它是缺陷，不是一种测试类型** | **已处理**：见「全量测试」一节末与 `FLAKY.md`。判据、排除清单、14 天时限都在那里 |
| **变异测试**（mutation testing） | 工具自动改坏源码（`>` 改 `>=`、返回值换常量），再跑测试；测试没失败就说明那一处没验到。它测的是**测试的质量** | **可选**：见「验收标准」一节「判断权在审查者」。依赖各语言各自的工具，没有通用入口，项目没有工具就仍靠走入口。**不挂进第 12 条** |

一句话区分：混沌工程制造**系统**的故障，不稳定测试是**测试自己**有随机性，变异测试改的是**源码**以检验测试。
